# 815 routers — measured, and the problem is not what it looks like

You asked whether we overdid it. Measured answer: **we did, but not in the way
the number suggests, and the fix is not deletion.**

## The funnel, measured

```
815 router modules
709 distinct URL prefixes          ← the real capability count
 13 advertised to a customer       ← core mode hides 696
 13 used by the 8-flow console     ← exactly the same 13
```

The funnel already works. A customer sees 13 things, not 709. Core mode does its
job — one loose `startswith` fixed earlier took the advertised surface from 455
paths to 308.

And the routers are not padding: median **220 lines**, only 4% under 120 lines,
212,533 lines of router code total. Every one of the 815 is mounted. Nothing is
dead. Deleting is not available as a lever — measured separately, removing 92 MB
of generated artifacts moved the repomix token count by **zero**.

## So where did we overdo it?

**Two places, and only two.**

### 1. Roughly 47 routers per capability

709 prefixes express about **15 real product capabilities**. That is not 709
products; it is one product sliced 709 ways, mostly one router per engine. The
API's shape mirrors the implementation rather than the customer's job — which is
the same disease the UI had at 300 pages for 8 flows.

56 prefixes are claimed by more than one router, and 157 routers share a prefix
with another. (An earlier pass here reported "23 routers claim
`/api/v1/connectors`" — that was a mismeasurement, string-containment rather
than prefix equality. Exactly **two** routers declare that prefix; the other 26
modules namespace *beneath* it. See the connectors section below.) That is where the duplicate-route problem lives: `GET /api/v1/findings`
has **three registered handlers** and only the first is ever reached. It cost
this project real time twice — a correct fix landed in a handler no request
goes to.

### 2. We hide almost everything we built

This is the finding that matters commercially. Aikido sells itself as
**"15-in-1 ASPM"**. We have built all fifteen. We surface **two**.

| Capability | Built | On the customer surface |
|---|---|---|
| SCA / dependencies | yes | **yes** |
| Risk graph | yes | **yes** |
| SAST | yes | hidden |
| Secrets | yes | hidden |
| Container scanning | yes | hidden |
| IaC scanning | yes | hidden |
| DAST | yes | hidden |

**We look like a narrow product because we are configured to look like one.**

## Which hidden ones actually work

"Built" by name is not proof, so I probed them with a real customer key. The
first pass guessed `/stats` for every capability and returned four 404s; those
404s were **my wrong path names, not missing capabilities**. Re-probed against
the routes that actually exist:

| Endpoint | Result |
|---|---|
| `/api/v1/sbom/stats` | **200** — `total_components`, `license_risk_high` |
| `/api/v1/dast/stats` | **200** — `scans`, `endpoints_tested` |
| `/api/v1/reachability/stats` | **200** — `node_count`, `by_language` |
| `/api/v1/autofix/stats` | **200** — `total_prs_created` |
| `/api/v1/sast/summary` | **200** — `{"status":"no_scan"}` |
| `/api/v1/secrets/` | **200** — tenant-scoped, echoes the caller's real `org_id` |
| `/api/v1/iac/summary` | **200** — real content, 35 builtin rules |
| `/api/v1/cspm/posture` | **503** — `{"status":"not_configured"}` |

**Eight of eight are real.** And three of them are real in the way that matters
most: `sast` says `no_scan` rather than "0 findings", and `cspm` says
`not_configured` rather than returning a clean bill of health for a cloud
account nobody has connected. Those are the honest-absence answers this codebase
was taught to give, and they are exactly what makes a capability safe to
advertise — an empty screen that explains itself is an onboarding step, not a
lie.

So the customer-facing surface went from **2 capabilities to 10**, and not one
line of new product code was needed to do it.

## The other thing the probe found: the vocabulary is a mess

Grepping the prefixes behind these capabilities shows where the 709 really came
from:

```
container : /container /containers /container-security /container-posture
            /container-registry-security /container-runtime      (6 prefixes)
secrets   : /secrets /secrets-scanner /secret-scanner
            /secrets-manager /secrets-management /secrets-rotation (6)
license   : /license /licenses /license-scanner /license-security  (4)
cspm      : /cspm /cspm-engine                                     (2)
```

Six URLs for "container security" is not six capabilities. It is one capability
named six times, and it is the same disease as `GET /api/v1/findings` having
three handlers: nobody could tell which name was the real one, so each new
router invented its own.

## What to do — three moves, none of them "delete"

**1. Surface what already works.** *(done in this change.)* Nine prefixes added
to `_CORE_PREFIXES`: the eight verified above plus `/api/v1/graph`, which the
console's risk screen was already calling while core mode kept it out of the
advertised schema — a customer-facing dependency missing from the
customer-facing spec. The advertised surface goes from 13 capabilities to 23.

**2. Collapse the vocabulary.** Six container prefixes, six secrets prefixes,
four license prefixes. Pick one name per capability, alias the rest. This is a
routing and naming exercise, not a rewrite — the code stays, the surface becomes
legible. It is also the only durable fix for the duplicate-handler class of bug,
because that bug is a symptom of nobody knowing which name was canonical.

**3. Copy what connectors already got right.** `/api/v1/connectors` is the
largest single prefix on the surface — 117 of 472 paths — and the first read of
that number was that it must be the worst of the sprawl. It is the opposite.
Two routers declare the prefix and 25 more namespace beneath it:

```
/api/v1/connectors/crowdstrike-live   /api/v1/connectors/okta-live
/api/v1/connectors/defender-xdr       /api/v1/connectors/sentinelone
/api/v1/connectors/snyk-oss           /api/v1/connectors/jamf-live
/api/v1/connectors/cyberark-live      /api/v1/connectors/acunetix   … 25 total
```

That is not one capability sliced 25 ways. It is **25 named vendor integrations
under one capability namespace** — a catalog, and a thing to put on the pricing
page rather than clean up. 117 paths is what 25 integrations × ~5 endpoints
looks like when it is organised properly.

So connectors is the template, not the problem. `/api/v1/connectors/{vendor}` is
precisely the shape the container, secrets, and license families should take:
one namespace per capability, everything else beneath it. Six sibling
top-level prefixes for container security is the same content arranged badly.

## The cost of move 1, stated plainly

The advertised surface grew from **308 paths across 13 capabilities to 472
across 23**, measured by building the core-mode schema before and after.
Breadth and focus trade against each other, and this change spent some focus to
buy breadth.

That is the right trade here only because the alternative was worse: a buyer
comparing us to a 15-in-1 competitor was being shown two capabilities and
concluding, correctly on the evidence in front of them, that two was all we had.
The eight newly-surfaced capabilities add 128 paths — real growth, and the
honest price of no longer hiding the product from the people evaluating it.

## The honest summary

We did not build too much. We built roughly the right fifteen things, named
several of them six different ways, and then showed a customer two of them.

The sellability problem was **under-surfacing, not overbuild** — and the fix was
a nine-line change to a tuple. What remains is a naming problem, and connectors
already shows what the answer looks like.
